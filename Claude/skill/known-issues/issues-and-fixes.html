Issues & Fixes Log

What this is: a running log of real problems hit while developing software — the confusing symptom, the actual root cause, and the fix. Not a ticket tracker; no ticket numbers here on purpose.

How to use it: before spending time diagnosing an unfamiliar error (CI, e2e, tooling, git, coverage, etc.), search this page first. If the same or a similar symptom is listed, apply the fix directly instead of re-diagnosing from scratch.

Keeping it current: add a new entry whenever a new non-obvious issue + fix is found. Keep entries short — symptom, cause, fix, permanent prevention. No fluff.

Tooling ShedLock logs a DuplicateKeyException on a scheduled job's lock insert — looks like a startup error, isn't one

What went wrong

  • A DEBUG-level org.springframework.dao.DuplicateKeyException appeared right after startup, on a background scheduler thread, from an INSERT INTO ...ShedLock... statement — followed by "Initiating transaction rollback on application exception".
  • Looked alarming (a stack trace + rollback right at startup), but ApplicationAvailabilityBean had already logged ACCEPTING_TRAFFIC beforehand, and the exception is on a scheduling thread, not main.

How it was fixed

  • Not a bug — this is ShedLock's own lock-acquisition algorithm (JdbcTemplateLockProvider) working as designed. It always tries an INSERT first, optimistically assuming no one holds the named lock yet; if a row for that name already exists, the INSERT fails with a duplicate-key violation, which ShedLock's provider catches internally and falls back to a conditional UPDATE (succeeds only if the existing row's lock-until timestamp has passed).
  • Confirmed by checking the job's @SchedulerLock(lockAtMostFor=..., lockAtLeastFor=...) values — restarting within that window against the same shared lock table (often a table reused across services/instances) reproduces this every time, and it stops once the previous lock naturally expires.

Permanent fix / how to avoid

  • No fix needed — this is expected, self-resolving noise, visible only because DEBUG logging is on. The scheduled job tick is simply skipped that round; nothing crashes or fails to start.
  • Before treating a DEBUG-level exception near startup as a real problem, check which thread it's on and whether readiness/availability logs already flipped to healthy before it — a background scheduler/lock exception after that point is noise, not a startup failure.
  • If this pattern repeats indefinitely (never resolves after the lock's max-hold duration), that's the real signal something's actually stuck — e.g. a lock row with a lock-until far in the future from a bad clock or a crashed holder that never released it.
Tooling AWS CLI fails with "Unknown output type: JSON" even though credentials are valid

What went wrong

  • aws sts get-caller-identity (used as a quick credentials sanity check) failed with aws: [ERROR]: Unknown output type: JSON — exit code 255.
  • Looked like an auth problem at first, but the SSO session/credentials in ~/.aws/credentials were actually valid and not expired.

How it was fixed

  • Cause: ~/.aws/config had output = JSON (uppercase) under the [default] profile. The CLI's output-format value is case-sensitive and only accepts lowercase (json, text, table, yaml, yaml-stream) — an uppercase value makes every command using that profile fail before it even gets to auth.
  • Confirmed by overriding it per-command: aws sts get-caller-identity --output json succeeded immediately, proving the credentials were fine all along.

Permanent fix / how to avoid

  • Fix the config value itself: lowercase the output line in ~/.aws/config (e.g. output = json).
  • Or override per-invocation with --output json or the env var AWS_DEFAULT_OUTPUT=json (lowercase) without touching the config file.
  • Don't assume a CLI error mentioning credentials/auth-adjacent wording means the credentials are actually the problem — test with an explicit --output override before re-authenticating or requesting new creds.

What went wrong

  • An e2e job failed every single test with net::ERR_CONNECTION_RESET on the very first page load — across completely unrelated features/scenarios.
  • Retrying produced the identical failure, ruling out a flake.

How it was fixed

E2E Local e2e run blocked — no AWS credentials for test-data lookup

What went wrong

  • Running a non-mocked e2e scenario locally failed immediately on a setup step that fetches test data (e.g. a valid test account/id) from a backend service: Could not load credentials from any providers.
  • Cause: that lookup needs AWS credentials, and none were configured in the shell.

How it was fixed

  • Ran aws sso login --profile <profile> to refresh the expired SSO session.
  • Exported AWS_PROFILE and AWS_SDK_LOAD_CONFIG=1 before running the tests.

Fix attempt 2

  • Same symptom, valid (non-expired) SSO credentials already present in the shared credentials file under a named profile — aws sts get-caller-identity worked fine from the CLI. The e2e run still failed.
  • Root cause found in the test-data client's own auth helper: when no AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY/AWS_SESSION_TOKEN env var is set, it builds its credential provider as defaultProvider({ profile: process.env.AWS_PROFILE ?? process.env.DEPLOY_ENV }) — with AWS_PROFILE unset, it silently looks for a profile literally named after the run's target-environment value (e.g. a profile named "dev1"), which doesn't exist; the real profile is named after the SSO permission set (or is just default).
  • Fix: explicitly export AWS_PROFILE to a profile name that actually exists in ~/.aws/credentials/~/.aws/config (default works if that's the profile with valid credentials) before running the e2e command. AWS_SDK_LOAD_CONFIG wasn't needed for this — a plain named-profile lookup from the shared credentials file resolved fine without it.

Fix attempt 3 — no AWS access in the shell at all (e.g. a sandboxed agent environment)

  • Neither fix above is usable when the shell genuinely has no path to AWS credentials (no SSO, no static keys, no way to configure a profile).
  • The helper that does the discovery lookup already supports a pin-and-skip override via an env var — confirmed working: set that env var to a known-good test-data id before the run, e.g. <OVERRIDE_ENV_VAR>=<known-good-id> npm run test:local -- <spec-file-path>. This bypasses the AWS-backed discovery call entirely — no credentials needed.
  • Scope the run to the one spec file by path when using this, rather than --grep — a quoted --grep pattern passed through several layers of cross-env/npm-script/spawnSync did not reliably scope the run down (it silently ran the full suite instead in one observed case); the generated spec file's own path did.

Permanent fix / how to avoid

  • Before running any e2e scenario that isn't fully mocked, make sure the relevant AWS SSO profile is logged in — sessions expire and silently fail with a generic credentials error.
  • Don't assume an unset AWS_PROFILE falls back to default — some custom AWS SDK wrapper clients fall back to another env var (like the run's target-environment/lifecycle name) instead, which silently resolves to a profile that doesn't exist. Always set AWS_PROFILE explicitly to a profile name you've confirmed exists, and verify resolution with a throwaway script that prints only success/failure and a masked key prefix — never print full credential values.
  • If there's no AWS access at all in the shell, check whether the helper already supports pinning a known test-data id via an env var to skip the discovery lookup entirely — confirmed to work as a full substitute for AWS credentials, not just a fallback.
E2E Page-object element name with a digit throws "doesn't meet the requirements" at query time

What went wrong

  • Named two page-object children after numbered items on the page (e.g. 'Footnote 1', 'Footnote 2') to target each one directly.
  • Every step referencing them failed at query time: Error: The passed query item doesn't meet the requirements. Current queryItem: 'Footnote 1'.
  • Cause: the framework's element-name parser only allows letters/spaces/underscores in the name itself. A digit is only accepted as an ordinal prefix before the name (e.g. 1st Item), never inside the name — so any child key containing a bare number is rejected outright, not just when queried with an index.

How it was fixed

  • Replaced the two digit-suffixed keys with one collection selector matching every instance of that repeating element (e.g. all footnote paragraphs under their shared container).
  • Referenced them in Gherkin via the framework's own ordinal-prefix convention instead — '1st Footnote' / '2nd Footnote' — which the parser does accept.

Permanent fix / how to avoid

  • Never put a digit inside a page-object child key, even one that looks purely descriptive ('Footnote 1', 'Step 2') — it will fail this parser's naming rule regardless of whether the element actually repeats on the page.
  • If there's genuinely only one such element (not a real collection), give it a spelled-out or ordinal-free name instead (e.g. 'First Footnote', or just 'Footnote' if there's only one) rather than reaching for a digit.
  • If it does repeat, model it as an isCollection: true selector up front and rely on the framework's own 1st/2nd/3rd query syntax — don't hand-roll numbered keys.
Tooling npm swallows --grep passed through nested npm run scripts

What went wrong

  • npm run test:<env>:chromium -- --grep "Foo" failed with "No tests found".
  • The wrapper script chains multiple npm run calls; at the inner call, npm re-parsed --grep as its own flag instead of forwarding it, so "Foo" reached Playwright as a garbage file-path pattern.

How it was fixed

  • Bypassed the npm wrapper scripts — set the same env vars they set (target environment, base URL, API endpoints, etc.) manually.
  • Ran any code-generation step the suite needs (e.g. BDD spec generation), then called npx playwright test --grep "..." directly.

Permanent fix / how to avoid

  • Whenever a scoped/filtered e2e run is needed (--grep, a specific spec path), call npx playwright test directly with the required env vars instead of going through the chained npm run test:<env>:<browser> scripts.
E2E Link-to-a-downloadable-file scenario asserted the wrong thing

What went wrong

  • A scenario asserted that a new tab's URL contains the file's path after clicking a target="_blank" link to a downloadable file (e.g. a PDF). It timed out.
  • Chromium treats navigating to this kind of file as a download, not an in-tab view — the popup's window.location/title never change.

How it was fixed

  • Confirmed the behavior with a small standalone Playwright script before touching the real test — it showed a download event firing with the real URL/filename, while the popup page itself stayed blank.
  • Rewrote the assertion to listen for the download event and check its url() / suggestedFilename() instead of the popup's own URL.

Permanent fix / how to avoid

  • For any scenario where a link opens a downloadable asset in a new tab, assert on the download event — never on the new tab's page.url().
  • If unsure whether a resource downloads vs. renders inline, verify with a 10-line throwaway script before writing the real assertion.
Git Pre-push blocked — stale coverage report

What went wrong

  • git push repeatedly blocked with: "stale coverage report — source changed after it was generated".

How it was fixed

  • Ran npm run test (regenerates coverage/) immediately before pushing.

Fix attempt 2 — the generic "test" script never terminated

  • Symptom looked identical (push still blocked, coverage command "just kept running" for many minutes), but the real cause this time: the repo's package.json aliased the plain test script to interactive watch mode with a real, non-headless browser (--watch=true, no headless flag) — it never exits on its own, so it can never actually regenerate a fresh one-shot report.
  • A separate script (e.g. test:coverage) was the one the pre-push/pre-commit hooks and CI actually run — headless, single-pass, exits with a code.
  • Before assuming a coverage regen command is just slow, check the actual script body in package.json/build.gradle for a --watch/non-headless flag, and check for a differently-named one-shot script the hooks/CI actually invoke — don't assume the generic script name is the right one.
  • Killing a stuck watch-mode run can leave its whole process tree (npm → framework CLI → browser + all its child processes) orphaned rather than exiting, especially if the run was stopped by killing a wrapper/background-task handle rather than the process itself — check for an unexpectedly large number of the relevant node/browser processes before writing the slowness off as normal machine load.

Permanent fix / how to avoid

  • Always regenerate coverage as the last step before pushing, any time source changed since coverage was last generated — a hook that compares file modification times rather than content hashes can be triggered even by a rebase alone.
  • Use the exact script name the pre-push/pre-commit hook or CI config invokes, not whatever seems like the obvious generic name — confirm by reading the hook/CI config or the package script body once per repo.
Git PR/MR blocked — "Fast-forward merge is not possible"

What went wrong

  • The target branch (e.g. main/develop) advanced while the PR/MR was in review, so the fast-forward-only merge method rejected the merge. Can happen more than once in the same review cycle.

How it was fixed

  • git fetch → git rebase origin/<target-branch> → regenerate coverage → git push --force-with-lease.
  • Checked via the git host's approvals API/UI that this project does not reset existing approvals on a force-push (this is a per-project setting — verify it rather than assuming).

Permanent fix / how to avoid

  • When a project's merge method is fast-forward-only by design, expect to rebase (never merge-commit) whenever the target branch moves before your PR/MR merges.
  • Force-pushing your own feature branch afterward is normal here, not a bypass.
MCP A Node-based MCP server fails to reconnect (-32000) behind a TLS-inspecting proxy

What went wrong

  • A remote MCP server failed to reconnect with a generic -32000 JSON-RPC error — looked like a bad/expired auth token at first glance.

How it was fixed

  • Ran the underlying npx mcp-remote command by hand to see the real error: SELF_SIGNED_CERT_IN_CHAIN — a TLS trust problem, not an auth problem.
  • Traced it to NODE_EXTRA_CA_CERTS pointing at a CA bundle that didn't include the root certificate of a TLS-inspecting proxy. A newer bundle that did include it already existed on disk but wasn't wired up.
  • Repointed NODE_EXTRA_CA_CERTS at the newer combined bundle and restarted the app.

Permanent fix / how to avoid

  • If any Node-based MCP server/CLI fails to connect to an internal HTTPS host with a vague error, run its underlying command directly first — don't assume it's the token.
  • SELF_SIGNED_CERT_IN_CHAIN → check NODE_EXTRA_CA_CERTS includes the current proxy root cert bundle, then restart the app — Windows does not propagate env var changes to already-running processes.

Tooling A CLI workspace command silently reuses a stale directory from an unrelated prior run

What went wrong

  • A CLI command that opens a working directory keyed only by an id (e.g. /tmp/<prefix>-<id>), with a second argument (like a component name) that should scope a distinct branch, ignored that second argument when the directory already existed from an earlier, unrelated invocation for the same key.
  • The command's own JSON output reported the intended new branch name, but the actual checked-out git branch remained whatever a prior run had left checked out — a different, unrelated branch.
  • Committing and pushing on trust of the reported branch name pushed unrelated new work onto that stale pre-existing branch instead of a fresh one, and the stale directory also had unrelated uncommitted edits sitting in its working tree from the earlier run.

How it was fixed

  • After running the workspace-opening command, verified the actual checked-out branch with git -C <dir> branch -vv/git status rather than trusting the command's reported JSON — caught the mismatch before pushing anything further.
  • Left the stale directory and its uncommitted edits untouched (they may be another task's in-progress work), and instead hand-built a clean workspace: a fresh directory, a sparse git clone/checkout of the same repo at the target ref, git checkout -B <correct-branch> origin/<ref>, reapplied the drafted file changes there, then validated/committed/pushed from that clean directory.
  • Did not force-push over the stale branch to "fix" it in place — it had no open PR/MR and no destructive action was needed to make forward progress; flagged it for the user instead.

Permanent fix / how to avoid

  • Never trust a workspace-opening command's reported branch/path blindly when the same key may have been used in a prior run — always confirm with git branch -vv and git status in that directory before drafting or, especially, before committing/pushing.
  • If the directory turns out stale (wrong branch, or unexpected uncommitted changes not from this session), don't reuse or reset it — build a clean one by hand from the same remote/ref and proceed there.

Tooling A build-tool Gradle plugin passed --dry-run validation but crashed for real in CI

What went wrong

  • CI failed running a Gradle analysis task (e.g. sonarqube) after a Gradle major-version bump, with a NoSuchMethodError for a Gradle internal API the plugin still called (here: DslObject.getConvention(), removed in Gradle 9).
  • The same plugin version had earlier been validated via ./gradlew <task> --dry-run and reported as "configures cleanly" — that result turned out to be wrong.

How it was fixed

  • Reproduced locally by dropping --dry-run and running the task for real — same crash, same stack trace.
  • Bumped the plugin to a version built against the new Gradle major line; re-ran for real — the internal-API crash was gone (the task then only failed on missing local credentials/config, unrelated).

Permanent fix / how to avoid

  • --dry-run only configures/realizes the task graph — it never executes a task's action. A plugin crash that only happens deep inside the task's real execution (not during plugin application/configuration) will not be caught by dry-run at all.
  • When validating a build-tool plugin against a new Gradle major version, run the task for real at least once (even without full external connectivity/credentials) — a crash inside the plugin's own code shows up before any network call, so this doesn't require a live server to catch.
  • Don't generalize "plugin X survived dry-run" to "plugin Y will too" — each plugin's own internal-API usage decides whether the crash surfaces at configuration time (dry-run catches it) or execution time (dry-run misses it).
E2E Corrupted e2e node_modules type declarations fail the pre-push tsc build

What went wrong

  • A `git push` was blocked by the husky pre-push hook: the e2e package's `tsc` build failed with `TS2306 File '.../node_modules/@some-scope/some-lib/core/index.d.ts' is not a module` and `TS2307 Cannot find module '@some-scope/some-lib/core/.../types'`, across several unrelated source files.
  • The branch being pushed had no diff at all under `e2e/` — the failure was unrelated to the actual code change.

How it was fixed

  • Inspected the installed package's own `.d.ts` file directly — it only declared one unrelated internal module, missing all the real exports (logger, reporters, context, interceptors, etc.), confirming a stale/incomplete local install rather than a real type error.
  • Ran `npm ci` inside the e2e package directory to force a clean reinstall from the lockfile.
  • Re-ran the build — the `.d.ts` file now had the correct `export * from './logger'` etc. lines, and the push's build/lint pre-push step passed.

Permanent fix / how to avoid

  • If a pre-push (or CI) TypeScript failure references a package under `node_modules` with a nonsensical "is not a module" or "cannot find module" error, and the current branch has no diff touching that package or directory, suspect a corrupted/incomplete local install before assuming a real code regression.
  • `npm ci` in the affected package directory is the fast, safe fix — it wipes and reinstalls exactly per the lockfile, so it can't silently upgrade/change dependency versions the way `npm install` might.
E2E A live third-party API response crashed a test with "is not iterable"

What went wrong

  • An e2e assertion that spread two array fields from a third-party API's JSON response (e.g. [...response.data.someList, ...response.data.otherList]) crashed with TypeError: response.data.otherList is not iterable — on a real, successful (200) response.
  • The TypeScript interface for that response declared both fields as plain, always-present arrays, so nothing on the type-checking side hinted this could happen.

How it was fixed

  • Checked the backend service's own model for that same third-party payload — the field was an unannotated, nullable List with no non-null guarantee, confirming the third party genuinely omits the key (rather than sending an empty array) when there's nothing of that kind for the given request.
  • Made the field optional in the TypeScript interface (otherList?: Item[]) and defaulted with ?? [] at every read site.

Permanent fix / how to avoid

  • Don't declare a field from a third-party/external API response as always-present just because it usually is — check whether the backend's own model for that same payload treats it as nullable/optional, and mirror that in the client-side type instead of assuming a fixed shape.
  • If a strict linter (e.g. @typescript-eslint/no-unnecessary-condition) flags a defensive ?? []/?. as "unnecessary", that's a signal the *type* is overconfident, not that the defensive code is wrong — fix the type to be optional/nullable rather than removing the guard or suppressing the lint rule.
Testing Submitting a test sign-up with a company email fails "email failed verification"

What went wrong

  • A manual end-to-end test submitted a sign-up form using the tester's own company email (plus-addressed) and got 400 VALIDATION_ERROR "email failed verification".
  • The email-verification step rejects the company's own domains on purpose (a configured internal-domain list returns "invalid" without calling the verification provider), so employee addresses can never be used as an end-user email.
  • The test guide had assumed "internal domains skip the external check" meant they pass; they skip it and fail.

How it was fixed

  • Submitted with an address outside the internal-domain list; the submit then passed.
  • That alone does not get the email delivered in non-prod: the email-sending service has its own recipient allow-list/block-list and rejected every non-internal address tried (with or without + addressing, and a public webmail domain). Its record shows REJECTED / "Email sending rejected by defined rules" after the hand-off succeeded.

Permanent fix / how to avoid

  • Before writing test data, read the service's email-verification code/config for an internal-domain list and what it returns for a match.
  • Disposable/throwaway inbox domains also fail when the provider flags disposable or undeliverable addresses; use a real external mailbox.
  • A direct call to the notification/email-sending service usually skips this form-side check, so a company address works there.
  • When a test email is accepted but never arrives in non-prod, check the sending service's own request record and logs for a rules rejection before suspecting your own code.
  • The deployed allow-list/block-list is environment config, not the repo's local config. Don't infer the allowed domains from a local config file; ask the owning team for the deployed values, or to add the test address.
  • If the only domains the sender allows are the ones the form-side check blocks, no test address passes both; the sender's team has to allow-list one.
